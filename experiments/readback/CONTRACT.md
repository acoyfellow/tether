# Experiment: read-back check for Cloudflare API writes

Frozen before any check code or data exists. Changes after this commit go in a Deviations section with a reason.

## Claim

For a Cloudflare API write recorded in the shape of the `cloudflare-agent` `executed_writes` row, reading the resource back and comparing each `after` value catches writes that did not land as recorded. An "API said ok" check does not catch them.

## Record shape

```json
{
  "tool_name": "execute",
  "account_id": "...",
  "target": { "kind": "kv" | "d1" | "worker_tags", "...": "..." },
  "changes": [{ "key": "...", "before": "...", "after": "..." }],
  "result": { "success": true }
}
```

`target` is given as structured data. Deriving it from the generated code is out of scope here.

## Kinds

| Kind | Write | Read-back |
|---|---|---|
| `kv` | PUT a key in `gl-probe-kv` | GET the key value |
| `d1` | UPSERT a row with two columns in `gl-probe-d1` | SELECT the row |
| `worker_tags` | PUT tags on a `gl-sb-*` Worker script | GET the script settings |

## Cases

20 per kind, 60 total. Generated by a seeded script, then frozen to `cases.json` before the run.

- 10 honest: the write is applied exactly as recorded.
- 10 faulty, 2–3 of each of these, with the record still claiming success:
  - `never_applied`: the write call is skipped.
  - `wrong_value`: the write uses a different value from the record.
  - `overwritten`: the write is applied, then a second write changes it before the check.
  - `partial`: only the first of two fields is written. For `kv`, which has one field, this is replaced by `wrong_value`.

## Arms

- `api_ok`: verdict from the recorded `result`, the same rule as `classifyToolOutcome`.
- `readback`: read the resource and compare every `after` field.

## Metrics

Computed by `score.ts` from the per-case files in `runs/<run>/`.

- Recall on faulty cases.
- False alarm rate on honest cases.
- Median and maximum time per check.
- API calls per check.

## Pass rule

`readback` passes if all of these hold in each of 3 runs:

1. Recall = 1.0 on every kind.
2. False alarm ≤ 5% overall.
3. Median time per check < 1 s.
4. `api_ok` recall < 0.5, which shows the problem is real for this shape.

## Disproof exit

If `readback` misses any faulty case in any run, or false alarms exceed 5%, the claim is recorded as disproven with the failing cases named.

## Mutation check

Before scoring, `mutate.ts` must show that each comparison in `readback` matters: forcing any one field comparison to `true` must lower recall on the cases that change that field.

## Deviations

1. Before any run, `mutate.ts` failed on fields `a` and `tag0`: every `partial` case dropped the second field, so no case tested the first field's comparison alone. `gen.ts` now alternates which field is dropped. The cases were regenerated and frozen before run 1.
